# 项目文档组织方案:TODO + README + LOG + REPORT + DESIGN

> 本文阐述本项目(以及可推广到整个 jailbreak_research 仓库)的文档组织约定:
> 五种文档各自的职责、更新时机,以及**人类视角**与 **Agent(LLM 助手)视角**下如何阅读、如何维护。
> 本文件本身是"关于文档的文档",属于元文档。

---

## 一、五种文档的职责分工

| 文档 | 性质 | 回答的问题 | 存放位置 | 规模约束 |
|------|------|-----------|----------|----------|
| **TODO** | 前瞻(Forward-looking) | 接下来要做什么?卡在哪? | `docs/TODO.md`,**全项目唯一** | 任务清单,可勾选 |
| **README** | 状态快照(Snapshot) | 这个目录是什么?怎么用?当前成果? | **每个目录一个**(根/src/scripts/data/configs/output) | 稳定、随时间更新不积累历史 |
| **LOG** | 回溯时间线(Timeline) | 发生过什么?为什么改方向? | `docs/LOG.md`,**全项目唯一** | 只追加,一条事件一行,带日期 |
| **REPORT** | 研究结论(Findings) | 试了什么?结果如何?结论是什么? | `docs/REPORT.md`,**全项目唯一** | 按"尝试-结果-结论"单元组织,结论可修订 |
| **DESIGN** | 设计决策(Decision) | 为什么这么设计?有哪些取舍? | `docs/README.md`(或独立 DESIGN.md) | 设计图、对比表、FAQ |

### 核心原则

1. **职责不重叠**:README 是"现在长什么样",TODO 是"接下来做什么",LOG 是"过去发生了什么",REPORT 是"研究得到了什么结论",DESIGN 是"为什么是现在这样"。
2. **单一来源**:TODO / LOG / REPORT 全项目各只有一个;事件、任务、结论不分散到各 README。
3. **交叉引用不复制**:REPORT 引用 LOG 的时间点,LOG 引用 README/TODO 的结果与任务,不把内容复制一遍。
4. **LOG 只追加不改写**:LOG 是历史,写错不删,用新条目纠正。**REPORT 可修订**:结论随证据更新,修订时直接改对应单元,不追加"修正版"。

## 二、人类视角:怎么读、怎么用

### 2.1 阅读路径(按场景)

| 场景 | 看什么 |
|------|--------|
| 刚接手/隔了一周回来 | 根 README(项目是什么+当前状态)→ LOG 最近 3 条(发生了什么)→ TODO(现在要做什么) |
| 要写论文某章节 | DESIGN(docs/README.md:设计与对比)→ **REPORT(尝试-结果-结论单元,直接提炼数字与结论)**→ LOG 中实验起止与决策 |
| 组会/向导师汇报 | **REPORT(可汇报单元)** + 根 README 当前状态 |
| 要跑某个实验/脚本 | 对应目录 README(用法、GPU 布局、端口)→ 根 README 快速开始 |
| 遇到卡点/报错 | TODO P0(已知阻塞项)→ LOG(之前是否遇到过、怎么解决的) |
| 评审/汇报进度 | 根 README 当前状态 + TODO 勾选情况 + REPORT 结论 + LOG 时间线 |

### 2.2 维护纪律(人类)

- **完成任务时**:勾掉 TODO 条目;若产生成果,更新对应目录 README 的"实验成果";若是有意义的事件,追加一条 LOG。
- **完成一轮实验时**:在 REPORT 写/更新一个"尝试-结果-结论"单元;结论若被新证据推翻,直接修订该单元。
- **遇到卡点**:立刻在 TODO 记一条(标注卡点),解决后勾掉并在 LOG 记解决方式。
- **改变方向/决策**:DESIGN 更新新决策 + LOG 记一条"为什么"(背景与理由)。
- **不要**:把事件/结论写进 README(会膨胀)、在多个地方维护 TODO/LOG/REPORT(会失同步)、把结论写进 LOG(LOG 只记事件)。

### 2.3 写论文时的用法

- REPORT 是"实验章节"的第一手素材:每个单元 = 一段实验描述(尝试)+ 一张数据表(结果)+ 一句结论。
- LOG 是"研究过程"章节的素材:方向变更、AB 方案取舍、踩坑记录都有日期可查。
- README 的"实验成果"可提炼为论文中的数字摘录。
- DESIGN 的对比表(SESS vs PAIR vs Agentic)可直接转成论文中的对比表格。

## 三、Agent 视角:怎么读、怎么用

> Agent(如 Qoder)是这套方案的主要消费者之一。它无法"记住"跨会话上下文,
> 文档是它的外部记忆。约定越清晰,Agent 切入任务越快、越少瞎猜。

### 3.1 Agent 的切入路径(首次接触某目录)

```
1. 读根 README        → 项目定位、当前状态、目录导航
2. 读 docs/TODO.md    → 唯一任务清单,找到 P0/当前主线
3. 读 docs/LOG.md 尾部 → 最近发生了什么(环境变更、卡点、决策)
4. 读 docs/REPORT.md  → 已有研究结论(避免重复实验、结论可直接引用)
5. 按 TODO 领取任务   → 读相关目录 README 了解代码/脚本用法
6. 开始干活
```

Agent 的优势:不需要人类口头交代上下文——README 给了"现在",TODO 给了"下一步",LOG 给了"为什么",REPORT 给了"已知什么"。

### 3.2 Agent 的维护纪律(在 loop 中)

推荐的开发/实验 loop:

```
更新 TODO → 按 TODO 完成任务 → 子任务完成或出现反馈 → 更新 LOG(事件)/REPORT(结论)/README(状态) → 伺机更新 TODO → 循环
```

- **拿到新环境/新反馈**:先更新 TODO(环境变更、新发现的阻塞项),再动手。
- **完成子任务**:勾 TODO;若改变当前状态,更新根 README"当前状态";记录事件到 LOG。
- **完成一轮实验**:结果与结论写入 REPORT 对应单元(或新建单元);LOG 只记"跑完了什么"事件。
- **发现问题(如 CLI 不兼容)**:立刻在 TODO 记一条"反馈",写清现象与修法,避免下次重复踩坑。
- **Agent 特有纪律**:
  - 只维护 `docs/TODO.md`、`docs/LOG.md`、`docs/REPORT.md`,不新建第二份。
  - LOG 条目用"日期 — 标题"格式,正文用短横线列表,便于人类扫读。
  - 结论写 REPORT、事件写 LOG、状态写 README——**写错分类就修订,不混装**。
  - 修改代码时同步更新对应目录 README(接口、用法、已知问题)。
  - 不确定时先读文档再问人;文档没写的才去读代码。

### 3.3 文档对 Agent 的收益

| 收益 | 说明 |
|------|------|
| 免重复勘探 | 各层 README 说明代码/脚本,Agent 不必每次 grep 全库猜用途 |
| 上下文廉价重建 | LOG 让 Agent 在会话中断/重启后快速恢复"发生了什么" |
| 结论即用 | REPORT 让 Agent 直接引用已有结论,避免重复实验或重复得出结论 |
| 任务可达 | TODO 是唯一权威任务源,Agent 不会同时维护多个清单导致冲突 |
| 反馈闭环 | 卡点/CLI 问题记入 TODO,下次会话的 Agent 直接看到,不用重新发现 |

## 四、目录模板(可在新子项目复制)

```
<project>/
├── README.md          # 项目概述 + 环境准备 + 当前状态 + 快速开始 + 目录导航
├── docs/
│   ├── README.md      # DESIGN:设计文档 + 对比表 + FAQ
│   ├── TODO.md        # 唯一待办(含 P0 阻塞项 + 各 Phase)
│   ├── LOG.md         # 唯一事件时间线(日期 — 标题,短横线条目)
│   └── REPORT.md      # 唯一研究结论(尝试-结果-结论单元,结论可修订)
├── src/README.md      # 代码说明 + 实验成果 + 已知问题
├── scripts/README.md  # 脚本用法 + GPU 布局 + 端口 + 实验成果
├── data/README.md     # 数据来源 + 格式 + 统计
├── configs/README.md  # 配置说明
└── output/README.md   # 结果目录约定 + 实验成果汇总
```

## 五、FAQ

### Q: REPORT 和 LOG 有什么区别?有必要分开吗?

A: **有必要,语义不同**。
- LOG 是只追加的事实时间线(事件:环境变更、踩坑、实验起止),服务于"上下文重建"。
- REPORT 是可修订的研究结论(尝试→结果→结论),服务于"对外汇报与论文"。
- 关键差异:结论会随证据更新(比如子集结果被全量结果推翻),**结论必须能改,而 LOG 只追加不能改**。
- 混在一起时,改结论会破坏 LOG 的只追加纪律;分开后 LOG 条目变短更纯,REPORT 直接可汇报。

### Q: LOG 有必要吗?README 记进展不行吗?

A: 不行。README 是状态快照,LOG 是时间线。事件(决策、卡点、实验起止)是
**随时间排序的**,分散进各 README 后无法重建"为什么从方案 A 切到 B"。
LOG 是写论文研究过程、跨会话恢复上下文的关键。约束:只记有信息量的事件,
不记流水账;一条一行,带日期。

### Q: 为什么 TODO/LOG/REPORT 只维护一个?

A: 单一来源避免失同步。多个 TODO/LOG/REPORT 会互相矛盾,Agent 和人类都不知道听谁的。
各层 README 可以多个——它们描述不同目录,天然分散。

### Q: DESIGN 和 README 有什么区别?

A: README 回答"是什么、怎么用",DESIGN 回答"为什么这么设计"。
本项目把 DESIGN 放在 `docs/README.md`(设计文档 + FAQ),根 README 负责
项目概述与环境。若设计内容增多,可拆独立 `docs/DESIGN.md`。

### Q: 实验成果写在哪?

A: 数字/结论写在各目录 README 的"实验成果"小节(就近原则,方便快速查阅);
**研究结论与实验单元写 REPORT**(可汇报、可修订);"什么时候跑的、怎么跑的"
写 LOG;具体结果文件在 output/ 下,README/REPORT 只放摘要和链接。

### Q: Agent 和人类维护同一套文档会冲突吗?

A: 不会,只要遵守"LOG 追加不删改、TODO 勾选不改结构、REPORT 结论可修订、成果就近更新 README"
四条纪律。Agent 应主动更新(loop 中),人类复核即可。
